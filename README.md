# solari_files

Download San Miguel from <https://casual-effects.com/data> and extract into `raw/` so the OBJ is at
`raw/San_Miguel/san-miguel.obj`, then:

```sh
cargo run --release -p san_miguel_import -- raw/San_Miguel/san-miguel.obj assets/san_miguel san_miguel
```

Download Bistro (Amazon Lumberyard) from <https://developer.nvidia.com/orca/amazon-lumberyard-bistro>
as a PNG-textured `.glb`/`.gltf`, then:

```sh
cargo run --release -p bistro_import -- raw/Bistro/Bistro.glb assets/bistro bistro
```

Baked meshes are cached; pass `--replace` to re-bake. San Miguel also has `--floor-only` and
`--cutout-only` to emit a minimal single-object scene, and `--erode <px>` to tune the OMM cutout
mask. Run an importer with `--help` for all options.


# Terrain paint arrays (Poly Haven)

Downloads material maps from <https://polyhaven.com> (CC0, cached in `raw/polyhaven/`) and bakes
mipped KTX2 `texture_2d_array`s into `assets/terrain/` — albedo (sRGB) + normal + ARM, one layer
per material. With no slugs it bakes the 24-layer set: 0..=10 index-aligned to zero's `BiomeType`
(Ocean..Mountain), 11..=21 per-biome secondary variants (biome id + 11), 22 scree, 23 wet
drainage mud; `terrain_layers.json` records the layer↔slug mapping.

```sh
cargo run --release -p polyhaven                    # 11-biome set at 1k
cargo run --release -p polyhaven -- --res 2k        # same set, 2k
cargo run --release -p polyhaven -- snow_02 ...     # custom layer list
cp assets/terrain/terrain_*.ktx2 /mnt/code/p/zero/assets/terrain/
```

# Trees (SpeedTree, NVIDIA ORCA)

Source: <https://developer.nvidia.com/orca/speedtree>. Drop the pack under `raw/SpeedTree_v2/`
(one dir per tree, each with `HighPoly/*.fbx` + `Textures/*.dds`). Two stages — the `gltf` crate
can't read FBX and `image` can't read DDS, so Blender does both, then the Rust stage bakes clusters
+ an OMM on every leaf cutout.

Stage A — FBX → glb (embedded PNG, base-color alpha preserved):

```sh
mkdir -p raw/SpeedTree_v2/_glb
for d in raw/SpeedTree_v2/*/HighPoly; do
  tree="$(basename "$(dirname "$d")")"
  blender -b --python scripts/speedtree_to_glb.py -- \
    "$d"/*.fbx "raw/SpeedTree_v2/_glb/${tree// /_}.glb"
done
```

Stage B — glb → one `<Tree>.bsn` each + shared `meshes/`/`textures/`:

```sh
cargo run --release -p speedtree_import -- raw/SpeedTree_v2/_glb assets/speedtree
```

Foliage is classified from the base-color alpha histogram (not the glTF alpha mode), so leaf/frond
materials get `AlphaMode::Mask` + a 2-state OMM (100% known → zero any-hit on leaves) while bark/caps
stay opaque. `--replace` re-bakes meshes, `--scale`/`--erode`/`--level` tune size/OMM. FBX author
units are cm; the baked entities carry a 0.01 scale so trees land metric (White Oak ≈ 7.6 m).


# Zero-Day (Beeple, NVIDIA ORCA) — the first ANIMATED asset

Download from <https://developer.nvidia.com/orca/beeple-zero-day> and extract under `raw/ZeroDay_v1/`
(`MEASURE_ONE/`, `MEASURE_SEVEN/`, each a `.fbx` + `tex/*.dds`). Two stages: Blender decodes the FBX +
DXT `.dds` (the Rust crates can't), then `zeroday_import` bakes a **hierarchy-preserving** `.bsn`
(this asset carries rigid TRS animation) plus a compact `.animclip`.

```sh
# Stage A — FBX → geometry glb + meshless anim glb (one run, matching node names)
blender -b --python scripts/zeroday_to_glb.py -- \
  raw/ZeroDay_v1/MEASURE_ONE/MEASURE_ONE.fbx raw/ZeroDay_v1/_glb/measure_one

# Stage B — glb → assets/zeroday/{MeasureOne.bsn, MeasureOne.animclip, meshes/, textures/}
cargo run --release -p zeroday_import -- \
  raw/ZeroDay_v1/_glb/measure_one.glb assets/zeroday MeasureOne
```

Optional checks: `python3 scripts/glb_json.py <file.glb>` (inspect a glb), plus the generic
headless `.bsn` load (no GPU) and a clip round-trip:

```sh
cargo run --release -p prop_import --bin load_test -- "$PWD/assets" zeroday/MeasureOne.bsn
cargo run --release -p prop_import --bin clip_check -- assets/zeroday/MeasureOne.animclip DynamicCamera2
```

Use `prop_import`'s `load_test`, not `zeroday_import`'s — the generic one registers the animation
component, so it actually loads an animated `.bsn` instead of silently reporting 0 for everything.

Render in zero (solari_files is just the asset factory — copy the output over, then run the example):

```sh
cp -r assets/zeroday /mnt/code/p/zero/assets/
cd /mnt/code/p/zero && cargo run --example zero_day
```

Deferred: DirectX normal green-flip, opacity/transmission, emissive nit tuning.


# Hoverboard (authored) — the first TEXTURE-FREE asset

Unlike everything above, this one isn't downloaded — it's generated by a Blender script that lives
with the .blend at `/mnt/code/p/assets/hoverboard/` (see its README to rebuild the model itself).

Its materials are procedural (Noise/Voronoi/Pointiness), and none of that crosses glTF. Baking them
to maps would work, but would buy detail at the cost of texture reads — the measured bottleneck in
this renderer. So the export **flattens** each graph to the scalar factors `StandardSolariMaterial`
already carries (`base_color` / `metallic` / `perceptual_roughness` / `emissive`) and ships no
textures at all: the ray tracer shades the whole prop from the `GpuMaterial` struct, zero samplers.
No UV unwrap is needed either, since nothing samples.

Within-panel variation is the thing given up. It's bought back at PANEL level — the deck's gap
booleans already cut it into 5 plates, and each takes its own wear variant (`hb_core.DECK_WEAR`), so
nose and tail read scraped while the sheltered middle stays clean. Extra material slots are cheap;
texture fetches are not.

Stage A — .blend → glb (flattens materials, drops the render stage, neutralizes the hero pose so
the prop is authored at origin):

```sh
blender -b /mnt/code/p/assets/hoverboard/hoverboard.blend \
  --python scripts/asset_to_glb.py -- --out raw/hoverboard/hoverboard.glb \
  --collection HOVERBOARD --neutralize-root Hoverboard_Root --flatten \
  --emissive-scale 200 --bake-res 64
```

Stage B — glb → `assets/hoverboard/{hoverboard.bsn, meshes/}` (`textures/` stays empty):

```sh
cargo run --release -p prop_import -- raw/hoverboard/hoverboard.glb assets/hoverboard --scene-name hoverboard
cargo run --release -p solari_view -- assets/hoverboard/hoverboard.bsn
```

Headless check (no GPU) — asserts the factors survive the round trip and that nothing pulled in a
texture handle. Note the absolute asset root; a relative one resolves against the crate dir:

```sh
cargo run --release -p prop_import --bin load_test -- "$PWD/assets" hoverboard/hoverboard.bsn
```

This asset is why `gltf.rs` now emits the scalar factors it used to defer. `base_color` is a `Color`
ENUM, so it needs a tuple-variant literal — `Color::LinearRgba(LinearRgba { .. })` — where the other
fields are plain structs; that was the reason it was deferred. A wrong type path there bakes
cleanly and fails only at load, which is what `load_test` guards.

**Emissive is authored in NITS on export, not in the .blend's numbers.** The Cycles values are
scene-relative (tuned against tens-of-watts area lights and a -0.1 view exposure); Solari is
physical and exposes at `Exposure::BLENDER` (EV100 9.7 → a ~0.001 multiplier), so a strip at 8.5
radiance lands at 0.0085 and reads BLACK. `hb_core.EMISSIVE_NITS_SCALE` (×200) converts on export
only — raising the Blender values instead would blow out the hero render. The strips land ~1700
nits, the thruster core ~5200, the holo panel ~345; compare the shipped assets at 100 / 2000 /
20000. This is the same 0-1-vs-physical trap the `Exposure` inspector section exists to rescue.

Deferred: the holo panel flattens to an OPAQUE emitter (Solari approximates every non-Mask alpha
mode as a 0.5 cutout, which would punch holes in it rather than read as a hologram). Edge chipping
is edge-only in the shader and averages out of the flattened factor — `vertex_custom` + a custom
chit is the texture-free way to get it back if it's wanted.


# Ships (Vattalus, itch.io) — the first PURCHASED-asset intake

Four modular sci-fi ships from `assets/itch.io/`, baked with the shared stage-A script and the
generic importer. Each keeps its textures (the default for a purchased asset — flattening would
throw away authored maps to save reads it already paid for).

```sh
cd raw && for s in PhalanxCorvette PraetorGunship RhodesBattlecruiser TemplarFrigate; do
  d=$(echo "$s" | sed 's/\([A-Z]\)/_\l\1/g;s/^_//')
  unzip -q -o "/mnt/code/p/assets/itch.io/uploads_files_860985_VattalusAssets_${s}.zip" -d "$d"
done
```

Stage A per ship (`--retex` is what makes these usable at all):

```sh
blender -b --python scripts/asset_to_glb.py -- \
  --input raw/phalanx/PhalanxCorvette/PhalanxCorvette_Equipped.FBX \
  --out raw/phalanx/phalanx.glb --retex raw/phalanx \
  --variant Weathered --color Blue --emissive-strength 2500 --origin base

cargo run --release -p prop_import -- raw/phalanx/phalanx.glb assets/ships/phalanx \
  --scene-name PhalanxCorvette --asset-prefix ships/phalanx
cargo run --release -p solari_view -- 'assets/ships/*/*.bsn'
```

| ship | length | meshes | materials |
|---|---|---|---|
| PhalanxCorvette | 81.5 m | 3 | 3 |
| PraetorGunship | 100.5 m | 4 | 4 |
| TemplarFrigate | 138.2 m | 4 | 4 |
| RhodesBattlecruiser | 278.4 m | 11 | 7 |

What these needed, and why `--retex` exists: absolute authoring paths (`D:\Work\...`) in the MTL;
engine/turret textures unresolved while the hull's resolved; the FBX importer wiring a Unity
Smoothness map into `Specular IOR Level` with nothing reaching Metallic or Roughness; and kit
sub-parts shipping 3ds Max PLACEHOLDER materials (`01 - Default`, `Turret1`) that name no image at
all — those are matched by object NAME against texture dirs, expanding paired folders
(`Turret_M1_S1` serves `Turret_M1` and `Turret_S1`).

Known gap: Praetor's `Turret1` mesh resolves to no texture set — its name carries no model hint and
two turret sets exist, so it stays a flat colour rather than guess. The run warns.

Not done: the ships SHARE engine and turret models (12 of 48 texture names are common), but each
bake emits its own `.cluster_mesh`, so the geometry is duplicated rather than instanced. Baking the
parts once as a kit (`--per-group`) and referencing them would let the ships share a BLAS.


# Mech (authored) — the first RIGGED asset

DRV-4 "Drover", a ~9.2 m reverse-jointed bipedal walker, generated by the Blender scripts at
`/mnt/code/p/assets/mech/` (see its README to rebuild the model or drive the rig).

Texture-free like the hoverboard, but unlike everything above it ships a **joint hierarchy**.
Geometry is authored at a NEUTRAL bind pose with identity object transforms and bound to 13 joint
empties at real pivots; the hero stride, torso yaw and gun elevation are joint ROTATIONS, not
baked vertices. Animating it in-engine is rotating named entities.

```sh
# geometry, at the bind pose
blender -b /mnt/code/p/assets/mech/mech.blend --python scripts/asset_to_glb.py -- \
  --out raw/mech/mech.glb --collection MECH --neutralize-root Mech_Root --rest-pose \
  --flatten --emissive-scale 80 --bake-res 64
# meshless anim glb (joints only) + bake + validate
blender -b --python /mnt/code/p/assets/mech/build/anim_cli.py -- raw/mech/mech_anim.glb
cargo run --release -p prop_import -- raw/mech/mech.glb assets/mech \
  --scene-name DRV4_Drover --anim raw/mech/mech_anim.glb
cargo run --release -p prop_import --bin load_test -- "$PWD/assets" mech/DRV4_Drover.bsn
cp -r assets/mech /mnt/code/p/zero/assets/
cd /mnt/code/p/zero && cargo run --release --example mech
```

| | |
|---|---|
| height | 9.21 m (bind bbox 6.39 x 7.53 x 9.21) |
| node entities | 144 (131 meshes + 13 joints) |
| materials / textures | 30 / 0 |
| emissives | 8 entities, peak 2240 nits |
| clip | 12 KB, 10 targets, 2.00 s walk cycle @ 30 fps |

This asset is why `prop_import` grew `--hierarchy` and `--anim`, and `asset_to_glb.py` grew
`--rest-pose`.

**`--hierarchy` is mandatory for anything rigged.** The default flat path (`bake_gltf_scene`)
bakes every primitive to a WORLD transform and emits nothing at all for a transform-only node —
so all 13 joint empties would vanish and their children would freeze exactly where they were
baked, leaving the game nothing to rotate. `--hierarchy` routes to the same `bake_gltf_hierarchy`
zeroday uses: nested `Children[]`, LOCAL transforms, meshless nodes kept as `Name` + `Transform`.
It differs from `zeroday_import` only in not stamping the animation marker on the root unless
`--anim` is given.

**`--rest-pose` zeroes the ROTATION of every empty** so a rigged source ships at its bind pose and
joint rotation 0 means rest. Locations are deliberately left alone — those are the pivots.
`--neutralize-root` only reaches one object, which is not enough once the pose is spread across a
chain. Confirmed by the printed bbox: the exported dims match a `pose=False` build exactly.

**`--anim <glb>`** implies `--hierarchy`, transcodes the meshless anim glb into
`<scene>.animclip`, and stamps `bevy_animation::animclip::AnimatedScene` on the `.bsn` root — the
same wiring `zeroday_import` does, but as a flag rather than a bespoke crate. The clip binds by NAME-PATH, so
only the joint nodes need matching names between the two glbs; `anim_cli.py` therefore deletes all
geometry and exports the 13 joints alone, which both shrinks the clip to 12 KB and sidesteps the
`.001` suffixes the geometry export picks up converting curves and text to mesh.

The clip format, its loader and the name-path binding now live in **`bevy_animation::animclip`**
(moved out of zero's `bsn_anim` crate, which is deleted). Nothing in it was scene-specific — it
needs `AnimationTargetId`/`AnimationPlayer`/`AnimationGraph` plus `Name`/`Children`, all of which
`bevy_animation` already owns — so it added no new inter-crate dependency, and stock
`AnimationPlugin` now registers the loader and the wiring system. Apps get it for free from
`DefaultPlugins`; there is no plugin to add.

That move is also what makes `load_test` honest. While the type lived in zero, solari_files could
not register it, `DynamicBsnLoader` hard-errored on the unknown type, and the entire scene failed
to load reporting 0 for every count — which reads exactly like a broken bake. `zeroday_import
--bin load_test` had been doing that silently since it was written; it now reports 8642 named
entities and 7293/7293 cluster meshes. Note `register_asset_reflect::<AnimationClip>()` is what
lets the `.bsn`'s bare path literal coerce into a `Handle<AnimationClip>`; with only `init_asset`
the loader reports `type mismatch`.

Verified in-engine (`cargo run --release --example mech` in zero): 131 RT meshes, ankles
alternating between 0.950 (planted, exactly `ANKLE_Z`) and 1.495 peak — a 0.545 m lift against the
authored 0.55, with the two legs never both airborne. Sample the gait at an interval that does NOT
divide the 2.00 s clip period or every sample lands on the same phase and a working gait reads as
frozen.

Deferred: hydraulic rams are split so cylinder and rod ride different bones, but the rod does not
slide, so a large joint rotation stretches the pairing; cables are bound to one bone and deviate
across a bending joint. One clip only — no idle, turn or aim states.


# Viewer

Run from the repo root, passing a tab-completed path (add `--features dlss` for DLSS):

```sh
cargo run --release -p solari_view -- assets/lunarbase/KB3D_LNB_Bench_A.bsn
```

Pass a glob to load several scenes at once — each match becomes a row in the bottom-left picker;
click a row or press `[`/`]` to switch the live scene:

```sh
cargo run --release -p solari_view -- 'assets/lunarbase/KB3D_LNB_BldgLG*'
```

Quote the glob so the viewer expands it (an unquoted glob the shell already expanded works too). With
many matches the picker can run taller than the window; `[`/`]` still cycle through every scene even
when a row is clipped off-screen.

Or install the `solari_view` binary and run it from here:

```sh
cargo install --path crates/viewer
solari_view assets/lunarbase/KB3D_LNB_Bench_A.bsn
```



# Vulkan 

To install lastest sdk
```bash
curl -L https://sdk.lunarg.com/sdk/download/1.4.350.1/linux/vulkansdk-linux-x86_64-1.4.350.1.tar.xz \
  -o /tmp/vulkansdk-1.4.350.1.tar.xz
sudo mkdir -p /opt/vulkan/1.4.350.1
sudo tar -xf /tmp/vulkansdk-1.4.350.1.tar.xz -C /opt/vulkan/1.4.350.1 --strip-components=1
```

set in shell

```bash
source /opt/vulkan/1.4.350.1/setup-env.sh
```

test its working

```bash
echo "$VULKAN_SDK"   # should now read .../1.4.350.1/x86_64
```
